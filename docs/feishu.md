# 网页绑定飞书与投递恢复

工程版已经实现下面的绑定、收发与持久化流程，并通过 CLI 替身和浏览器契约测试。真实飞书应用的授权、权限和收发仍需在线联调。本指南用于真实配置环境；样例工作台会展示页面并关闭外部操作。

## 在网页完成配置

1. 启动工程版 API 与 Worker，打开“连接与设置 → 飞书连接”。该页也可通过 `/connections?tab=feishu` 直接进入。
2. 选择“创建新应用”并开始绑定，或选择“绑定已有应用”填写 App ID、App Secret。新应用流程会展示 CLI 返回的原始链接和对应二维码，使用自己的飞书完成页面操作。已有应用的 Secret 通过 stdin 交给 CLI 管理，提交成功后清空网页输入框。
3. 在开发者后台开启机器人能力，设置自己的可用范围，开通 `im:message:send_as_bot`、`im:message.p2p_msg:readonly`；使用长连接接收方式订阅 `im.message.receive_v1`，完成应用发布。若 CLI 返回权限配置链接，工作台会将原始链接和二维码一并展示。
4. 等待“消息通道就绪”。修改平台配置后，可点击“重新检查消息通道”。页面会显示缺少的权限和通道错误；后台对中断执行重连。
5. 点击“生成配对码”，在与该机器人的**单聊**中发送配对码。有效期为 10 分钟。配对成功后，页面自动展示实际用户与单聊标识。
6. 核对页面的接收对象、机器人身份和测试消息正文，点击“以机器人身份发送测试消息”。获得成功回执后，启用“飞书收发与摘要推送”。

新建应用的授权流程支持取消和过期后重新发起。重新配对会建立新的接收对象绑定，清除旧测试状态，后续发送需要重新验证。解除绑定会停止监听和后续发送；已经发出的请求保留在投递记录中。

飞书是可选入口，网页的模型、邮箱、摘要和查询配置可以先完成。

## 日常使用

- 直接在配对单聊询问邮件事项，随后继续追问。查询与网页复用同一个应用服务；两个渠道分别保存会话上下文。
- 新问题先回复“已收到，正在检索相关邮件并生成回答，请稍候”，随后发送最终答案；同一消息事件只产生一份接收提示。暂时故障自动重试时继续等待，最终失败会回复安全的错误原因与下一步。
- 发送“现在汇总一下”或 `/digest`，生成并回复当前摘要。
- 摘要请求也先发送接收提示；没有符合范围的邮件或同步覆盖未确认时，回复检查结果，避免只收到“请稍候”而没有后续。
- 发送 `/new` 或“新建对话”，下一次问题进入新的飞书会话上下文。
- 每日汇总按网页中的时间、时区和账号范围运行。只有汇总计划与飞书收发都启用时，定时摘要才会投递到飞书。
- 网页摘要详情中可以点击“推送这份摘要到飞书”，该按钮展示机器人身份与当前接收单聊。

摘要与查询回复使用方案一“简洁通知”，通过现有 `post` 富文本发送；长消息继续分段。工作台仅处理已配对用户在对应单聊中的文本或富文本消息。

## 简洁通知格式

新生成的邮件列表查询按“需要处理、待确认、等待反馈、按需查看”展示；每项重点保留真实邮件标题、下一步、邮箱名称和发件人。两封以上普通通知合并成一段，展示数量和最多三个主题，可继续追问具体内容。重点事项不会限制为两项。

每日摘要沿用已有分析的“优先处理、需要关注、信息通知”，不将优先级直接改称待确认或等待反馈；无明确截止时间的低优先级通知合并展示，有截止时间的事项仍单独列出。摘要保留实际统计范围、时区与版本。

下面是查询回复的示意，数量和内容仅用于说明排版：

```text
来信提醒

今天没有新增待办，近期有一项需要确认、一项等待反馈。

1 项待确认 · 1 项等待反馈 · 4 封按需查看

【待确认】新设备登录提醒
下一步：核对是否本人登录；本人操作可忽略。
来源：学习邮箱 · 邮箱服务

【等待反馈】申请材料已提交
下一步：等待审核结果，留意后续通知。
来源：学习邮箱 · 申请受理中心

【按需查看】其他通知 · 4 封
账号通知、欢迎介绍、激活确认等，可按需查询详情。

邮件依据：学习邮箱 · 本次引用 6 封邮件。
说明：部分邮件仅有正文片段，相关判断以当前可见内容为限，请核对原文。
```

数量只代表本次结果，不代表邮箱全部邮件；覆盖不足、同步失败及正文片段提示继续展示。来源使用回答或摘要保存的快照，不在消息中追加内部邮件编号；完整分析仍保存在网页。历史文字回答继续保留原文和来源名称，不补造事项分类。格式转换不增加模型请求，不改变已入队投递的正文；失败重试仍发送首次入队的原文。

## 核对与重试

“连接与设置”和“任务记录”均提供飞书投递记录。生成摘要与发送摘要分别保存状态；投递失败不会抹去已保存的摘要。已收到成功回执的分段会被跳过，重试使用原有正文和幂等键。

接收提示、最终答案与执行失败提示分别保留投递记录。新请求的通知意图保存在任务中，Worker 定期恢复缺失提示；不会回补通知功能上线前的历史失败任务，也不会将旧绑定的提示转发到新绑定。

模型查询分为工具检索和结构化回答两个阶段。最终回答使用新的 Agently 请求，关闭工具调用，仅使用本轮已读正文与检索范围记录；未完成正文读取时明确失败，不把它当作没有邮件。旧回答的文字不进入最终事实生成，只保留追问所需的用户问题和历史来源标识。

如果进程在请求发出后中断，或者未取得可核实的回执，记录标为“发送结果不确定”。先在飞书核对，再勾选明确的重试选项。远端幂等机制有时间边界，因此这类重试仍可能产生重复消息。重新绑定后的旧投递不会转发给新的接收对象。

## 部署与实现约定

API 持久化绑定请求、配对状态与投递意图；Worker 独占授权子进程、事件监听和实际发送。授权与投递使用独立任务通道，不占用网页查询通道。事件监听按 CLI 的 ready 标记判断就绪，并保持 stdin 打开；停止时关闭 stdin，再有序结束进程及当前 profile 的事件总线。

项目使用 `LARKSUITE_CLI_CONFIG_DIR=<数据目录>/feishu/cli` 和显式 `--profile` 访问独立配置。二维码保存在同数据目录下的私有目录，通过需要登录的 API 返回。应用 Secret 只在临时加密交接记录中保留，CLI 配置完成后删除该交接记录。运行产物与 CLI 凭据一起进入后续备份／恢复验收。

本次核对版本为官方 `lark-cli 1.0.97`。配置命令的本地 JSON 与消息 API 的 `ok/data` 信封分开解析。运行源码依据：[配置目录与 workspace](https://github.com/larksuite/cli/blob/v1.0.97/internal/core/workspace.go)、[应用初始化](https://github.com/larksuite/cli/blob/v1.0.97/cmd/config/init.go)、[新应用授权链接输出](https://github.com/larksuite/cli/blob/v1.0.97/cmd/config/init_interactive.go)。收发参数和事件结构同时对照本机 `--help` 与 `event schema im.message.receive_v1 --json`。

真实联调需核对：新应用／已有应用授权、实际权限缺失提示、二维码与链接有效期、消息通道 ready、本人配对、测试回执、自然语言追问、09:00 推送、真实网络中断及服务重启。替身测试不能代替这些结果。
