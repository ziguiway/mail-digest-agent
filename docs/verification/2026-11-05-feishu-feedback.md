# 飞书无回复与等待反馈修复

日期：2026-11-05（Asia/Shanghai）。已部署 `mail-digest-agent:0.2.0-feishu-feedback`，本地服务仍为 8877。

## 已确认的原因

用户在 16:45 发来的邮件处理问题已经被飞书监听器接收，任务执行过检索与多次正文读取，随后约 62 秒后以 `model_query_error` 结束；没有生成 assistant 消息，也没有创建最终回复投递。监听器一直 ready，因此这次无回复发生在模型生成环节。

只读复现得到 Agently 的 `ValueError: Can not satisfy ensure keys ... within 3 retries`，内部为 `Missing ensure key: answer`，约 83.60 秒后失败。原先的工具定义同时作用于检索与最终输出请求，模型继续调用工具或返回无法满足最终结构的内容，SDK 随后反复尝试解析。Worker 原有失败分支只记录任务错误，没有向飞书回复。

## 实现

- 查询分为两个阶段：Agently 原生工具检索最多四轮，最终使用全新的无工具结构化请求。两阶段合计继续受 150 秒限制，引用仍须通过已读来源校验。
- 最终输入包含本轮正文、实际检索范围、分页及覆盖提示。保留用户历史问题和历史来源，移除旧 assistant 回答文字，避免旧统计参与本轮事实生成。
- 检索到邮件却未读正文时明确报告 `mail_read_incomplete`；结构解析失败报告安全的 `model_output_error`，不误报为邮箱无邮件。
- 新飞书问题先产生一份独立 `request_ack` 投递，查询完成后再发送结果；摘要请求也提供接收提示，并为无邮件／覆盖未确认提供最终说明。
- 最终失败产生独立 `request_error` 投递；暂时故障仍自动重试时，不提前发送最终失败通知。错误说明只使用已净化的任务错误。
- 新任务保存通知意图，Worker 周期性恢复缺失的接收／失败提示；投递按绑定、类型、任务 ID 去重。通知不上溯历史失败任务，不越过旧绑定向新对象发送。
- 接收提示与查询分别使用 delivery、interactive 通道，不等待模型生成才发送接收提示；投递记录保留回执及原有重试机制。

没有数据库迁移或 API 契约变更。网页投递记录增加接收提示、执行失败提示的中文名称。
