# 智能查询超时与旧错误残留修复

日期：2026-11-05（Asia/Shanghai）。已部署至本机 `http://127.0.0.1:8877`。

## 现场证据

问题任务 `d070edbe0d71428bb1e0da10b89cfe55` 在 11:10:33 开始，首轮检索及阅读工具均已执行，但 150 秒总时限到达后触发自动重试。第二次在 11:13:13 开始，11:14:57 成功结束，已保存助手回答；整轮约 264 秒。

旧前端恢复 queued／running 任务时直接展示 `task.error`，成功轮询时又只在存在新错误时更新提示，没有清除旧值。因此截图中能同时出现“正在检索”和上一轮失败提示，成功后旧提示也可能继续保留。

现场 DNS、TLS、模型认证可用。使用已保存配置进行独立原生工具探测返回 HTTP 200、约 2.32 秒，模型确实返回工具调用。原结构化规划链路在同一句问题的候选检查中仍耗时约 138.5 秒，说明不能只修改错误文案。

## 最终修改

- 查询和连接探测使用 Agently 原生工具轮次，最多分别为四轮和两轮。
- 从三个只读 Action 的真实函数签名及类型注解生成函数工具 JSON Schema，保留必填参数和默认值，并明确写入 `OpenAICompatible.request_options.tools`。锁定的 Agently 4.1.4.10 提供者没有自动把 `prompt.tools` 转成该 HTTP 字段，仅切换协议会漏传工具定义。
- Action 在当前 Agent 上显式绑定，执行、工具结果、最终结构化结果解析及已读来源校验继续由现有链路处理，没有放开额外工具。
- 精简送给模型的历史记录，增加不重复检索、待办查询不把“今天／处理”作为必含关键词等指令。最终引用仍必须来自本轮实际读取的邮件。
- 查询异常复用安全错误分类：超时、网络、认证、额度、限流分别提示；未知兼容性错误不再自动重跑三次完整查询。
- Worker 领取重试任务时清除当前错误，原失败仍保存在 TaskEvent 中。前端只把最终 failed／cancelled 的任务错误作为失败提示，任务恢复及后续成功状态会清除旧错误；暂时无法读取状态的提示也会在恢复后清除。
