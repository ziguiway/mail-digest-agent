# 智能查询方案一：聊天内简表

日期：2026-11-05（Asia/Shanghai）。已实现并部署至 `http://127.0.0.1:8877/chat`。

## 行为与数据

- 新生成的待办／邮件列表回答采用一句总览与四列表格：处理建议、邮件事项、建议下一步、邮件依据。
- 处理建议区分需要处理、待确认、等待反馈、按需查看，不将状态等同于紧急程度。
- 两封及以上普通通知合并成一行，可展开逐封查看；原文按钮关联真实来源邮件 ID。
- 标题、邮箱标签、收件时间和正文片段标记来自已读取邮件，模型只返回来源 ID、处理建议及下一步。
- 表格行必须覆盖全部引用且不能重复，未读来源、错误状态或无效格式拒绝保存。正文截断标记对应本轮实际交给模型的内容长度。
- 手机端转为纵向事项布局，继续提供展开及原文入口。解释、比较或没有匹配邮件的回答允许使用完整文字。
- `messages.presentation` 保存带版本的结构化展示；`content` 保留完整文字，包括各行事项及建议，兼容历史上下文及飞书文本投递。已有消息保留原文，新生成的表格在刷新后仍可查看。

数据库新增迁移 `0006_query_tables`，在 `0005_digest_refresh` 上添加 nullable JSON 列。旧消息不补造分类、时间或处理建议。

## 真实模型验证

使用已保存的模型配置与专用测试邮箱缓存，只读执行“今天有什么需要我处理的邮件？”。最终代码返回一条表格行和一个已读来源，处理建议为 notice，引用与行的来源集合一致，耗时 11.09 秒；执行了 search_mails、read_mails。

本次查询选择的相关来源只有一封，不能将它解释成邮箱全部只有一封。多行与四封通知合并由独立固定数据页面测试验证。诊断没有写入用户对话或发送消息，耗时仅代表这次观测。
